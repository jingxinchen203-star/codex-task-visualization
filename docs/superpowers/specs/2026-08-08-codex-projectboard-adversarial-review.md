# Codex Projectboard 对抗性审查记录

日期：2026-08-08
被审查规格：`2026-08-08-codex-projectboard-design.md`
结论：`REVISED — PHASE 0 GO/NO-GO REQUIRED`

## 1. 审查方法

从三个互不依赖的视角先寻找失败场景，再决定是否保留设计：

- 产品反方：如果看板做成了，用户是否仍然不知道该继续什么？
- 体验反方：如果数据很多、窗口很窄、只用键盘或服务离线，界面是否仍可完成任务？
- 工程与安全反方：如果进程崩溃、版本分裂、两端同时写入或本机存在恶意进程，承诺是否仍成立？

审查不是投票。与用户已经明确确认的需求冲突、但没有更强证据的意见不直接采用；能构造具体损害路径的意见按 P0/P1/P2 修改规格。

## 2. P0：已修改

| 风险 | 原设计的失败方式 | 修订后的约束 |
|---|---|---|
| 整理不等于恢复 | 用户面对漂亮看板仍需重读长对话 | 新增跨项目“需要我处理”、`ResumePacket`、下一步来源与失效语义；目标为 15 秒定位、30 秒恢复。 |
| 一次验证过多高风险假设 | 注入、App Server、调度、Git 任一失败拖垮整个产品 | 拆为 Phase 0–3；先只读整理，再手动执行，最后受控自动化。 |
| CDP 不是安全边界 | 同用户本地进程可扫描端口并控制 renderer | 优先 debugging pipe；禁止 CSP bypass；端口模式必须显式披露风险，失败转独立 UI。 |
| App Server 版本/账户分裂 | PATH CLI 与桌面 helper 写入不同状态或协议不匹配 | 禁止裸 PATH；记录 binary hash、协议、账户主体与数据根，不一致只读。 |
| 崩溃后重复 Run | 远端已接受请求、本地未落库，重启后再次启动 | durable command journal + client request ID + fencing token；无法对账时 unknown，不自动重放。 |
| 事后检测双写太晚 | 原生 Codex 与 Projectboard 同时发起 turn | 只接受原子 lease/conditional start；否则专用线程 + 显式控制权转移。 |
| 审批可过期或串实例 | 旧页面批准了已变化的命令 | 新增 `ApprovalRequest` 身份、摘要、范围、过期和对账；仅 human-ui 可响应。 |
| Agent 可伪造测试证据 | MCP 写入 `exit_code: 0` 就进入待验收 | Agent 证据降为声明；Core verifier 在绑定 worktree/commit 上产生不可变 system evidence。 |
| 本地 API 可被网页跨站调用 | loopback 不等于可信，EventSource/query 泄漏凭据 | 精确 Host/Origin、Bearer、JSON + 自定义头、无副作用 GET、fetch streaming、单次 nonce。 |
| 五列在窄窗失效 | 只能看 1–2 列且出现双向滚动 | ≥1440px 保留五列全高标准形态；窄窗切成五状态单列视图。 |
| 拖放误触发执行 | 整理卡片意外创建 Run | 状态菜单为主路径；跨状态先确认与补全；自动运行默认关闭，倒计时常驻且可聚焦取消。 |

## 3. P1：已修改

- 全历史仍按用户要求扫描并默认归档，但最近/待处理内容优先索引，归档页提供最多 5 个有理由的建议恢复项。
- 项目卡从纯计数改为“项目名 → 唯一最高优先下一步 → 辅助计数”。
- Task 状态和 Run 状态采用不同视觉与状态来源；外部变化触发 reconciliation 和 stale 提示。
- SQLite 增加单写入队列、WAL、外键、乐观更新、活动 Run 唯一索引、事务 outbox 和一致性备份。
- Git 在排队时冻结 base OID，仓库写操作串行，重新校验状态并拒绝 junction/symlink 越界。
- 全量导入增加 scan generation、高水位、catch-up pass、有限 thread/read 预算和 10k 压测。
- 增加安装、单实例、签名升级、数据库迁移/回滚和卸载保留数据协议。
- 定义 loading、empty、partial、offline/read-only、error、unknown 和 success 的界面行为。
- 任务详情改为状态驱动的决策界面；待验收优先展示验收清单、改动、验证和风险。

## 4. 明确没有采用的反方意见

### 取消项目与五列看板

未采用。用户已明确确认“顶层项目 + 项目内五状态全高纵向泳道”，且这一结构对长期多项目工作有价值。修订方式是加入跨项目注意力入口和恢复包，避免看板沦为纯分类工具。

### 只扫描最近 30 天

未采用。用户明确要求自动扫描全部历史并统一放入归档。修订方式是全历史渐进扫描、最近价值优先、首屏不等待全量、所有建议仍需用户确认。

### 完全取消 Codex 内注入

未采用。注入是用户的明确核心诉求。修订方式是把它变成可拔插入口而非数据依赖：必须先通过安全闸门；失败时产品仍由独立 UI 完整可用。

### 第一阶段立即交付自动调度与 worktree

未采用为 Phase 1，但保留为目标形态。理由不是减少愿景，而是这些能力扩大了写入权限和不可逆损害，需要独立证据后再放权。

## 5. 剩余硬风险

以下问题不能靠文档推理消除，只能由 Phase 0 真实试验判定：

1. 当前 Windows Store 应用是否可靠接受调试 pipe/参数并复用同一用户数据根。
2. 可否在不 bypass CSP 的条件下稳定挂载 UI。
3. 桌面应用与可用 App Server 是否共享账户、数据根、线程可见性和兼容协议。
4. 协议是否提供足以防止双写和关联崩溃前后请求的原子能力。
5. 审批事件是否能在断线、重启和实例变化后安全对账。
6. 独立 UI 与注入 UI 的本地认证是否能抵御浏览器跨站调用和低权限本地进程。

任一 P0 失败都必须触发规格中写明的降级路径，不能把“测试没证明”解释成“以后再修”。
